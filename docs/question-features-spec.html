Three question features: what students see, what the database needs

Question Bank, PYQ Mix and Past Papers all draw from the same 18,651 questions. What separates them is how much time a student has.

The three, at a glance

FeatureSessionUnitClockFeedback
Question Bank2 minOne questionNoneInstant, per question
PYQ Mix20 minA set of 20YesScore at the end
Past Papers3 hoursA whole real paperYes, sectionalScore + section breakdown

A student picks by the time they have, not by the content — the questions are the same in all three. AI-Curated Exams is not a fourth feature; it is PYQ Mix with the questions chosen by weakness instead of at random. One toggle, not one more menu item.

Shared foundation: five tables

Everything below sits on these. Only two of them are about content; the other three record what a student did. 

papers            one row per source document
  paper_id        primary key — which document this is
  exam_key        which real exam it recalls (many papers → one exam)
  bank role       SBI / IBPS · PO / Clerk / RRB
  exam_type year  Prelims / Mains · 2019
  shift           often null
  duration_min    total time, for mocks
  total_marks     for scoring
  is_canonical    show this one, hide the near-duplicate recalls
  source_pdf      provenance

directions        passages, shared by several questions
  paper_id        ← part of the key. IDs repeat across papers
  direction_id    d001…d030
  body            the passage text

questions
  q_id            primary key
  paper_id        which document it came from
  q_num           position in that paper
  section         Reasoning / Quantitative / English / GA
  topic           finer than section
  difficulty      1–5
  direction_id    nullable, resolved with paper_id
  stem            the question
  options         { a…e }
  answer          'a'…'e'
  explanation     why
  marks           usually 1
  negative_marks  usually 0.25 — banking exams penalise wrong answers
  content_hash    same question from two sources = one row
  is_active       retire a bad question without deleting it

attempts          one row per sitting
  attempt_id  user_id  mode('bank'|'mix'|'paper')
  paper_id    null unless mode='paper'
  started_at  submitted_at  score

attempt_answers   one row per question answered
  attempt_id  q_id  chosen  is_correct  time_ms

Two things worth calling out. directions is its own table because the passage text is currently copied onto every question that shares it — and passage IDs repeat across papers, so the key must be (paper_id, direction_id). And attempt_answers is what makes mastery possible; without it the grade rail has nothing to measure.

01 Question Bank 2 minutes

What the student sees

A, B, C, D and E sit in a row… │ │ │ │ ( ) 3rd to the right │ │ (•) 5th to the left │ │ ( ) 2nd to the left │ │ ( ) 3rd to the left │ │ │ │ [ Check ] Skip → │ └────────────────────────────────────────────┘
  • One question at a time. Answer, told right or wrong, next.
  • No clock, no submission. Close the app mid-question and nothing is lost.
  • The counter is scoped to the filter — 12 / 240, not 12 / 18,651. A finishable number, not a demoralising one.
  • Filters live in the address, so a link can be shared.

How questions are selected

SELECT q.* FROM questions q
JOIN papers p USING (paper_id)
WHERE q.is_active
  AND p.bank = $1 AND p.year = $2 AND q.section = $3
  AND q.q_id NOT IN (already answered by this user)
ORDER BY q.q_num
LIMIT 1 OFFSET $n

One at a time, skipping what they've already done. No timer means no attempts row — just an attempt_answers entry per question, which is what feeds mastery later.

What the student sees

┌────────────────────────────────────────────┐ │ Build a set │ │ │ │ How many [ 20 ▾ ] │ │ Section [ Reasoning ▾ ] │ │ Years [ Any ▾ ] │ │ │ │ Source (•) Mixed from past years │ │ ( ) Target my weak areas │ │ │ │ [ Start ] │ └────────────────────────────────────────────┘ then: Q 7 of 20 ⏱ 13:42 left

How questions are selected

-- Mixed: spread across years, balanced by difficulty
SELECT q.* FROM questions q
JOIN papers p USING (paper_id)
WHERE q.is_active AND q.answer IS NOT NULL
  AND q.section = $1 AND p.bank = $2
ORDER BY random()
LIMIT 20;

-- Weak areas: same, but weighted toward topics
-- the student gets wrong most often
ORDER BY (SELECT accuracy FROM user_topic_mastery
          WHERE topic = q.topic AND user_id = $me) ASC,
         random()
LIMIT 20;
Note the answer IS NOT NULL. A timed set that cannot be scored is worse than no feature — so this screen stays behind the answer-key work.

How questions are selected

-- No sampling. The paper is the paper.
SELECT q.*, d.body AS passage
FROM questions q
LEFT JOIN directions d
  ON d.paper_id = q.paper_id       -- both keys, always
 AND d.direction_id = q.direction_id
WHERE q.paper_id = $1
ORDER BY q.q_num;
The join uses both paper_id and direction_id. Passage IDs are only unique inside a paper — all 30 of ours repeat across papers. Join on direction_id alone and students read a passage from the wrong exam.

Extraction: getting questions in

The source is 305 JSON files in the question-bank repo, one per paper, with questions nested inside. Two ways in, one shared function.

Bulk — a command, not a screen

bun run db:import ../question-bank/India/banking/papers-deduped --dry-run

  305 papers · 18,651 questions
    new          305 papers, 18,651 questions
    duplicates   0
  ⚠ 419 questions have no options   → marked inactive
  ⚠ 18,651 questions have no answer → cannot be used in timed modes
  • Dry run first, always. It reports what would change and writes nothing.
  • Safe to re-run. Keyed on paper_id, with content_hash per question. Running it twice changes nothing — which matters, because every parser improvement means running it again.
  • Uploading 305 files through a browser is the wrong tool; the questions live in git, so the sync belongs in a script.

Ongoing — the admin screen

  • Drop in one or more JSON files.
  • Same preview, then confirm.
  • Calls the same function as the CLI — one code path, so they can't drift.
